Load Agent Architecture

How the agent follows a broker’s SOP for one load, drawn from the code in this repository, and how a broker is onboarded without code. The worked example is load 481207 (Client A, broker id northline): the delay risk turns high at 07:00, the driver asks for the PO number at 07:12, and the agent escalates when its second ETA request goes unanswered. The second one is Acme Freight, whose own PDF procedure becomes a published SOP version with a new intent and a POD requirement.

Event flow, end to end

One agent run

Validator rules (domain/rules.py), checked per action against the state the earlier approved actions leave, by the action tool at the call and again in validate: recipient is a contact of the load (high), channel allowed for that contact, SMS rate limit (3 per contact per 60 min), the obligation exists, deferral policy (one deferral, at most 15 min), the attempt cap of the obligation’s kind (2 ETA requests in the standard catalog), no duplicate action, no phone number or email address in the text (high), the stage only moves forward. The loop’s budget per broker (BrokerLimits): max_steps tool rounds (8; 0 is the single plan), max_cost_usd per run (0.05) and max_rejections (3, then a BLOCKED_TITLE escalation with the accepted actions).

The deferral race (scenario G1)

SOP resolution

Advantages

The common path is deterministic: the same event and load always select the same sections, and the run record keeps their ids. The prompt holds a few sections instead of a broker’s whole manual, which keeps cost and latency down. A situation no tag names is searched before it goes to a Hero. A broker’s layer holds only what that broker changed, and no other broker’s sections are visible to its loads, by rules or by search.

Disadvantages

Search ranking is not exact, so the evals assert which tools and sections a run used, not a score. Editors still tag each section with the broker’s intents and stages, which the publish lint checks, and triage must classify a message into the broker’s intents correctly. Embeddings need a live model at publish; offline runs use a deterministic fake.

Budgets

Enforced in code: the 240 s run deadline and 60 s per model call (RuntimeConfig), and per broker the agent loop’s max_steps rounds, max_cost_usd per run and max_rejections (BrokerLimits). Measured: the queue age against the 5-minute SLA and the cost per load against $1, flagged at 80% (application/metrics.py). The per-step ceilings and the spend split are targets; the wave 3 bake-off measures the loop’s latency and cost (evals/RESULTS.md).

Most events cost little: skipped runs (duplicates, stale timers, empty messages) make no model call, risk changes, timers and processed documents skip triage, and a triage no-op ends after one small call. The plan in docs/answers.md 5.3 puts a typical load at about $0.07 on the current agent model; the bake-off replaces it with the measured cost.

Alternatives considered

OptionWhy not
One long prompt: full SOP and full history on every eventA 100-page SOP is roughly 50 to 70k tokens. Sent on about 80 events per load it breaks the $1 budget, and unrelated procedures push the model to act when it should not.
Compile SOPs into a workflow engineDeterministic, but every SOP change would need an engineer, and plain-English SOPs are ambiguous. We keep a small state machine for obligations only (attempts, deferral, timers); the steps stay in English.
One agent per stage or roleEach handoff adds a model call and drops context. The stage is already a selection key for SOP sections, so a separate agent adds latency and nothing else.
Vector search as the only way to find a sectionA missed section means silent wrong behavior that a test cannot assert. Search is the second step: the sections selected by intent and stage come first, and the agent searches only when they do not cover the event.
Tools that execute actionsAn action tool here only stages: it checks the action with the rules and answers accepted or refused, and the executor applies the whole plan in the commit, so a bad answer can be refused but never half-applied.
One structured plan per event (before wave 3)Kept per broker as max_steps: 0. As the default it cannot search, read a document on demand or correct itself after a refused action.
SOPs written in our format by engineersA broker’s own PDF is compiled into a draft and reviewed instead; the sops/ files remain the seed and the format a person can edit by hand.
