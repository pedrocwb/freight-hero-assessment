Load Agent Architecture

How the agent follows a client’s SOP for one load, from the first location ping to the POD. Worked through for load #481207 (Client A): delay risk turns high at 07:00 and the agent escalates at 08:02.

System overview

  • One event, one run. Each input is a typed event. The per-load queue allows one run at a time, so the agent never races itself on the same load.
  • No memory in the agent. State is the event log, the obligation ledger and the timer service. Each run rebuilds its context from them.
  • Procedures are data. Rules pick the SOP sections for an event. The model reads them and decides; it does not search for them.

Inside one run

How the SOP is chosen

Advantages

Deterministic: the same event and state always pull the same sections, and the run log records which ones. Prompts stay small, which keeps cost and latency down. A client edit cannot leak into another client.

Disadvantages

A situation with no tagged section finds nothing. The run then escalates to the Hero team and records an SOP gap for the authors. Authors must pick an event name for each section, which the editor constrains to a known list.

Alternatives considered

OptionWhy not
One long prompt: full SOP and full history on every eventA 100-page SOP is roughly 50 to 70k tokens. Sent on about 80 events per load it breaks the $1 budget, and unrelated procedures push the model to act when it should not.
Compile SOPs into a workflow engineDeterministic, but editors would need an engineer for every change, and plain-English SOPs are ambiguous. We keep a small state machine for obligations only; the steps stay in English.
One agent per stage or roleEach handoff adds a model call and drops context. Stage is already a retrieval key, so a separate agent adds latency and nothing else.
Vector search over SOP textA missed section means silent wrong behavior and cannot be asserted in a test. Kept as a fallback for events with no tagged section, never as the primary path.
